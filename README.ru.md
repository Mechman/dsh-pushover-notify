# dsh-pushover-notify

Pushover-уведомления для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness).

Харнесс рассчитан на работу без присмотра: он может думать и работать минутами,
а человек нужен ровно в трёх случаях. Плагин сообщает именно о них, так что DSH
можно оставить фоном, а Pushover становится его строкой состояния:

| Событие харнесса | Уведомление |
|---|---|
| Агент вызывает `ask_user_question` | **❓ Нужен твой ответ** + текст вопроса, priority 1, sound `cosmic` |
| Ждёт решения по разрешению (`approval/asked`) | **🔐 Нужно разрешение** + инструмент и причина, priority 1, sound `siren` |
| Ход завершён (`turn/end`, `completed` / `max-tokens`) | **✅ Агент закончил** + последний текст ассистента, priority 0 |
| Ход упал (`turn/end`, `error`) | **⚠️ Агент остановился с ошибкой** + текст ошибки, priority 1 |

По умолчанию молчит: субагентские сессии, прерванные вами ходы и завершения,
которые перекрыл следующий `turn:start` (goal-раунды, задачи планировщика).

## Зачем ещё один плагин

В экосистеме DSH уже есть сильные многоканальные решения (`dsh-notifier`,
`dsh-notification`, `cc-notify-hooks`). Этот плагин сознательно сделан наоборот:

- **Один канал, но до конца.** Приоритеты, звуки, устройства и разбор ошибок API
  Pushover — вместо абстракции «каналов».
- **Ноль зависимостей.** Только встроенные модули Node и глобальный `fetch`.
  Никаких shell-скриптов, `jq`, нативных модулей и сборки.
- **Только поток Session-событий.** Подписка на `ctx.on('session/event', …)`:
  работает в любом профиле (Desktop, Web, headless) и не вмешивается в
  конвейеры инструментов и другие плагины.
- **Конфиг — JSON-файл, который можно править на ходу.** Без перезапуска и
  мастеров настройки.
- **Достаточно мал, чтобы прочитать целиком** — один модуль ~330 строк и тесты
  на `node --test`.

## Установка

### Из npm, через менеджер плагинов DSH

```bash
dsh plugin add dsh-pushover-notify --profile <имя-профиля>
```

Пакет объявляет bundle-патч, который монтирует строку `pushover-notify`.
После установки один раз перезапустите поверхность (или дождитесь перезагрузки
профиля).

В приложении Desktop то же самое делается на странице **Plugins**.

### Из клона репозитория (без registry)

```bash
git clone https://github.com/Mechman/dsh-pushover-notify.git
```

и направьте строку профиля прямо на модуль — в `~/.dsh/cordis.patch.yml`
(или в `cordis.patch.yml` самого профиля):

```yaml
- insert:
    - id: pushover-notify
      name: file:///C:/src/dsh-pushover-notify/src/index.mjs
```

Файлы патча отслеживаются, поэтому строка подхватывается без перезапуска.
Проверить, что она попала в композицию: `dsh --profile <имя> --dump-config`.

## Настройка

Создайте `~/.dsh/pushover.json` (или `$DSH_HOME/pushover.json`):

```json
{
  "token": "application-api-token",
  "user": "user-key",
  "language": "ru",
  "notifyOnStartup": true,
  "notifyOnCompletion": true,
  "notifySubagents": false,
  "completionDelayMs": 2500,
  "questionPriority": 1,
  "questionSound": "cosmic",
  "approvalPriority": 1,
  "approvalSound": "siren",
  "completionPriority": 0,
  "completionSound": "pushover",
  "errorPriority": 1,
  "errorSound": "siren",
  "timeoutMs": 12000
}
```

Ключи берутся на [pushover.net](https://pushover.net): регистрация → создание
приложения → **API token** приложения и ваш **user key**.

Файл перечитывается на каждое событие, правки применяются сразу. Порядок
источников: переменные `PUSHOVER_TOKEN`/`PUSHOVER_USER` → файл → `config` строки
в патче профиля. Если файла нет, плагин падает обратно на
`~/.config/opencode/pushover.json` — машина, которая уже уведомляет из OpenCode,
заработает без настройки. Полный пример: [`examples/pushover.example.json`](examples/pushover.example.json).

### Параметры

| Поле | По умолчанию | Смысл |
|---|---|---|
| `token`, `user` | — | Токен приложения и ключ пользователя Pushover. Без них плагин молча ничего не делает. |
| `language` | `en` | Язык текстов: `en` или `ru`. |
| `device` | все | Отправлять на одно конкретное устройство. |
| `notifyOnStartup` | `true` | Одно тихое сообщение (priority −1) при загрузке — проверка связки. |
| `notifyOnCompletion` | `true` | Отправлять ли сообщение о завершении хода. |
| `notifySubagents` | `false` | Уведомлять и о делегированных субагентах (им вы всё равно не ответите). |
| `completionDelayMs` | `2500` | Пауза перед сообщением о завершении; новый `turn:start` её отменяет. |
| `questionPriority` / `questionSound` | `1` / `cosmic` | Приоритет и звук для вопросов. |
| `approvalPriority` / `approvalSound` | `1` / `siren` | …для разрешений. |
| `completionPriority` / `completionSound` | `0` / `pushover` | …для завершённых ходов. |
| `errorPriority` / `errorSound` | `1` / `siren` | …для ошибок. |
| `startupPriority` | `-1` | Приоритет стартового сообщения. |
| `guiUrl`, `urlTitle` | — | Необязательная ссылка в сообщении (например LAN-адрес Web GUI; `127.0.0.1` с телефона не откроется). |
| `timeoutMs` | `12000` | Таймаут запроса к Pushover. |
| `dryRun` | `false` | Писать в лог вместо отправки — весь путь, кроме сети, остаётся проверенным. |

Приоритеты Pushover: `-2` молча, `-1` без звука, `0` обычный, `1` высокий
(обходит тихие часы), `2` требует подтверждения (плагин сам добавляет
`retry`/`expire`).

## Как решается, о чём сообщать

- **Какие сессии**: сессия с `header.origin === 'subagent'` или с
  `header.parentSession` — делегированный ребёнок, она молчит (если не включён
  `notifySubagents`).
- **Какие события**: `tool/call` с `name === 'ask_user_question'`,
  `approval/asked` и `turn/end`. `turn/end` с `reason.kind === 'aborted'`
  считается вашим собственным действием и игнорируется.
- **Один раз на ожидание**: вопросы дедуплицируются по `callId` инструмента,
  разрешения — по `approval.id`, завершения — по номеру хода. Повторные события
  не пришлют второе сообщение.
- **Без спама от goal-раундов**: `turn/end` планирует отправку через
  `completionDelayMs`, а `turn:start` той же сессии её отменяет, поэтому
  автономные продолжения не дают «готово».
- **Формат**: заголовок (до 120 символов) и одна строка —
  `содержание — «заголовок сессии» — папка`. Заголовок берётся из события
  `session/title`, папка — из заголовка сессии.

## Если не работает

| Симптом | Что проверить |
|---|---|
| Ничего не приходит | Заполнены ли `token`/`user`; включён ли `notifyOnStartup`; перезапускалась ли поверхность после установки. |
| Стартовое сообщение есть, о ходах нет | `notifyOnCompletion` не `false`; прерванные (`aborted`) ходы намеренно игнорируются. |
| Нет уведомления о вопросе | Агент должен вызвать `ask_user_question`, а не спросить текстом. |
| `Pushover rejected the message (4xx)` в логе хоста | Неверная пара token/user или приложение не разрешено для пользователя. |
| Всё приходит дважды | Смонтированы два плагина или дублирующая строка — уберите одну (`--dump-config` покажет строки). |

Предупреждения хоста пишутся с префиксом `[pushover-notify]`.

## Совместимость

- DeepSeek Harness `>=0.2.2-alpha.1` (проверено на Desktop `0.2.2-rc.1`,
  композиция `dsh-base` + `dsh-web-app`, HMR включён).
- Node.js `>=22.19` (глобальный `fetch`, `AbortSignal.timeout`).
- Клиентской части нет — в браузерном интерфейсе ничего не меняется.

## Разработка

```bash
npm test           # node --test, без сети, глобальный fetch подменён
npm run pack:check # состав публикуемого пакета
```

Тесты прогоняют плагин через синтетические Session-события и проверяют точные
payload'ы Pushover: вопрос/разрешение/завершение/ошибка, дедупликация, молчание
субагентов, отмена следующим ходом, локализованный текст, отсутствие ключей и
отказ API.
